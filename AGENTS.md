# team517 collaboration rules

Before code changes in every session: inspect status, branch and remotes; fetch origin; compare HEAD to origin/main and inspect incoming commits/diffs. Preserve local/untracked work. Use a dedicated working branch; commit and push coherent validated batches. Fetch periodically, before overlapping changes, final validation and any main integration. Never force-push, hard-reset shared work, use broad ours/theirs resolution or clean unknown files. Understand both sides of conflicts and preserve compatible intent. Report starting remote commit, branch, incoming work, conflicts/resolution, created/pushed commits, CI and synchronization state.

Visible-first development: unless correctness/security requires otherwise, prioritize visible experience, usability/navigation/responsiveness, directly exercisable features, then infrastructure. Keep working API/service/backend/repository architecture; no direct mobile business Firestore, no weakened authorization/location/push privacy. Do not introduce Maps or future services without explicit scope. Use Node22 and established validation. Native claims require actual rendered/exercised evidence; distinguish physical devices from emulators, docked from floating keyboards and API-driven fixtures from native taps. No secrets in source, logs or screenshots.

Device preference (Kevin, November 14): when the physical phone is not connected, proceed with emulator acceptance and maintain one consolidated physical-device checklist. Do not repeatedly request connection; run the queued phone checks together after Kevin reconnects it. Emulator results never count as physical-device passes.
