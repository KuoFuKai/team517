# Architecture

Sprint 7A extends only delivery infrastructure: committed `notifications` → separate `onDocumentCreated` trigger → `NotificationDeliveryService` → recipient `device_tokens` repository → isolated FCM `PushProvider`. Existing business transactions never await provider responses. Private attempt metadata is on the same Notification; public DTOs exclude it. Device registration is authenticated/transactional and token-hash unique, with generation-fenced cleanup after transfer. The mobile native adapter acquires tokens, while all persistence and tap authorization use HTTP APIs. See [push lifecycle, privacy, at-most-once limitations and build setup](push-delivery.md). Historical no-push descriptions below refer to the original sprint implementation; Sprint 7A adds delivery without changing those domain transactions.

November 10 native acceptance uses an Android SDK 55 development APK with the ignored Android Firebase client configuration for team517-dev. Auth/Firestore and business HTTP routes remain demo-team517 emulators. Only the isolated named FCM Admin app uses the externally supplied ADC credential through backend environment configuration. The native notification-launch config plugin forwards direct FCM/serialized Expo responses to the SDK in both onCreate and onNewIntent before the development launcher can redirect. JavaScript subscribes once across Auth restoration, deduplicates response receipts, waits for a ready session after account navigation reset and then fetches the recipient Notification/current authorized resource. Native intent data remains an untrusted routing hint. No privileged execution data or raw token is persisted in this navigation path.

The Expo app uses Firebase Authentication for email/password login. Its screens call `src/api/client.ts`, which obtains the current Firebase ID token and attaches `Authorization: Bearer <token>` to fetch requests. No Firestore client is initialized or imported.

`App.tsx` coordinates small development screens in `src/screens`. The configured API client composes public resource functions (`src/api/service.ts`) with a fetch transport (`src/api/transport.ts`). This keeps native Auth/persistence wiring outside testable HTTP code. Screens receive actions and public DTOs; they have no collection or repository knowledge. The transport handles timeouts and readable errors without retrying writes. A synchronous ref guards pending UI actions before React can render the disabled controls. Successful initialization loads contexts, and tapping a listed context fetches its detail from the backend.

Development API and Auth hosts are derived centrally from EXPO_PUBLIC_DEV_HOST; full URL overrides support custom endpoints. Node 22 is declared at the root and in workspaces, and Functions deploys on nodejs22. The local HTTP vertical-slice harness uses the same transport/service code with Firebase JS Auth and in-memory persistence. Native AsyncStorage and rendered React Native behavior require the documented device acceptance test.

The v2 HTTP function `api` mounts Express at `/api/v1`. The authentication middleware verifies tokens with Firebase Admin, including revocation checks. Routes validate input and delegate care-context behavior to a service. The permission module checks persisted application roles and active memberships; repositories alone access Firestore. `lastActiveRole` is a UI preference and never grants access.

`packages/contracts` contains public DTOs with ISO timestamp strings. Backend document models use Admin Timestamp values and stay in `functions/src/domain`. Explicit DTO conversion occurs in the service. Shared types are erased at compilation; deployed functions do not need a runtime contracts package.

Identity collections: `users`, `care_contexts`, `care_context_members`. Initialization uses a transaction and preserves the first saved role and timestamps. Context creation atomically writes a context and a manager membership. Membership IDs concatenate a generated 20-character context ID, `_`, and the Firebase UID; the fixed-length context prefix makes the pair unambiguous. Only care managers can create contexts. Any active member may view their context, regardless of global role. Roles chosen during initial onboarding are self-declared, not professional verification.

Sprint 2A adds exactly three collections: `locations`, `tasks`, `task_events`. Private document models live in `functions/src/domain/task.ts`. `TaskService` enforces lifecycle and publish validation; `TaskRepository` owns Firestore access. The authenticated task router validates strict request DTOs and delegates to the service. Locations have manual labels/addresses, optional paired coordinates, context/creator and timestamps. No map service is used.

Tasks start in DRAFT with backend-owned creator/context, offerCount=0 and timestamps. API-editable fields include title, helpType (a short internal category string), legacy instructions, publicInstructions, privateInstructions, time range, location, urgency, visibility and compensation metadata. Null clears a draft field; omission leaves it unchanged. A draft can be incomplete, but any provided numeric, date and enum fields must be well formed. Task summaries omit instructions and creator details; detail DTOs explicitly map public fields and ISO timestamps. Neither DTO exposes offerCount, activeAssignmentId or event metadata.

Current lifecycle: DRAFT -> OPEN -> HAS_OFFERS -> AWAITING_CONFIRMATION -> ARRANGED -> IN_PROGRESS -> COMPLETION_PENDING -> COMPLETED, with CANCELLED/DISPUTED exceptions. Normal cancellation is allowed only before execution. Editing remains DRAFT-only. Publishing still requires all fields, ordered times, same-context location, valid enums and compensation metadata. VOLUNTEER has no reward/money fields; POINTS requires a positive integer reward without money; PAID requires a positive amount/currency without points. No value is transferred. VERIFIED_HELPERS now enables eligible external discovery via a separate safe DTO, while the existing full Task/location APIs remain circle-authorized.

The centralized authorizer grants active members location reads and task/location creation. DRAFT visibility is restricted to the creator and active CARE_MANAGER memberships in that same context. Ordinary members cannot list or fetch somebody else's DRAFT, even if their global app role is CARE_MANAGER. OPEN and CANCELLED retain the existing active-context-member access policy. Editing, publishing and cancelling require active membership plus either task ownership or the context membership's CARE_MANAGER role. A global role or lastActiveRole alone never grants these rights. Mutations read user/membership and relevant location inside the same transaction as the task change, so membership and state changes participate in conflict detection.

List access first verifies context membership, queries that context, and applies the same centralized `canViewTask` policy before mapping DTOs. Detail access passes task owner/status into the authorizer. Filtering is entirely on the backend; no private draft summary or detail reaches a helper client. The current unpaginated query still reads all tasks for that context internally; future pagination must preserve visibility before page limits and must not simply filter client responses.

Draft creation writes Task + TASK_CREATED atomically. Changes write Task + TASK_UPDATED/TASK_PUBLISHED/TASK_CANCELLED atomically. Transactions re-read status, preventing duplicate publish/cancel events under concurrent requests. Task events are append-only through this API and never exposed as arbitrary internal data. Explicit changed draft saves emit one event containing only changed field names; no-op saves produce no event. There is no autosave.

Mobile `TaskWorkspace` coordinates list, draft editor, detail and location screens through `src/api/tasks.ts`. Drafts, Open and Cancelled tasks have separate list sections. Save Draft persists incomplete input and returns to the list; a draft can be reopened. Publish saves the edited fields before requesting the transition, then refreshes the list. Failed publication leaves the saved draft available and displays structured field errors. A synchronous action guard and disabled controls prevent overlapping taps. HTTP writes have no automatic retry and remain non-idempotent across process restarts; refresh after ambiguous network failure.

Sprint 3A Adds Offers and a pending Assignment; Sprint 4 extends the Assignment lifecycle. Sprint 2B AI input still uses the same DRAFT/publish operation, with no AI-specific matching behavior.

## Sprint 3A marketplace boundary

Offer and Assignment documents are private backend models. Only `offers` and `assignments` collections are added. Offer IDs are `{taskId}_{helperId}`. ACTIVE offers can be withdrawn/re-activated using the same document and original createdAt; updatedAt and compact events preserve each change. SELECTED cannot use the withdrawal path. NOT_SELECTED closes backups at confirmation or live Offers at Task cancellation; EXPIRED remains reserved.

MarketplaceService applies lifecycle checks and a centralized marketplace authorization policy; MarketplaceRepository performs transactions and all Firestore access. A transaction reads the task, actor's current user/membership, selected helper eligibility and relevant Offer before any writes. Offering atomically creates/reactivates the Offer, increments offerCount, moves OPEN to HAS_OFFERS and creates OFFER_CREATED. Withdrawal decrements safely, restores OPEN for the final response and writes OFFER_WITHDRAWN. Concurrent retries cannot double increment/decrement or create duplicate Offer records.

offerCount means ACTIVE + SELECTED records, excluding withdrawals; selection preserves it. After selection, backups stay ACTIVE and count alongside SELECTED. Selecting requires task creator or active same-context manager, HAS_OFFERS, an ACTIVE same-task Offer, current helper eligibility and no activeAssignmentId. One transaction creates an Assignment with PENDING_CONFIRMATION, marks exactly one Offer SELECTED, sets Task AWAITING_CONFIRMATION/activeAssignmentId and appends HELPER_SELECTED. Competing selection transactions conflict; only one commits. Backups become NOT_SELECTED at confirmation, as documented below.

Offer lists expose only minimal helper ID, available verification status, own supplied message/status and timestamps, with real rating/count aggregates where available and no fabricated names/profile details. Random members and competing Helpers cannot list Offers. Users can retrieve their own Offer only. Assignment reads allow the selected helper or an authorized task creator/context manager and return relationship metadata only—no location or private task instructions. Selection grants no new care-circle membership or private Task/location access.

Global HELPER role is required to offer. Active care-circle members are trusted for their context even if UNVERIFIED. Outside the circle, a user additionally needs server-controlled VERIFIED status and VERIFIED_HELPERS visibility. Discovery requires a VERIFIED global HELPER, excludes their own tasks and returns only published OPEN/HAS_OFFERS tasks. Verification uses an optional server-side User field defaulting to UNVERIFIED; no identity provider/self-verification endpoint exists. The explicit loopback demo seed supplies mock states for testing.

Task cancellation now closes actionable Offers and pending/confirmed Assignments atomically. Selected withdrawal uses the Assignment decline/cancellation flow. ACTIVE backup withdrawal before confirmation preserves awaiting state.

## Discovery and location privacy

DiscoveryService reads at most 100 eligible-status/visibility candidates, filters owner and optional urgency/compensation/radius on the server, and returns at most 30. One configured Firestore index supports visibility/status; results are not a complete nearest-neighbor search and no cursor exists yet. Coarse distance math is isolated in discovery/geo.ts for future geohash/index replacement without changing DTOs. Location reads are bounded by candidate IDs. Radius needs explicit coordinates, maximum 100 km; missing task coordinates are omitted from radius searches.

TaskDiscoveryItemDto explicitly whitelists public title/help type, schedule, urgency, compensation, response count and approximate location. It never includes street address, stored label, access instructions, Location ID, context/receiver/creator identity or the raw Task/Location document. The same DTO is used for safe detail, List and Map-mode development views. Private instructions are deliberately omitted entirely; publishers must keep private data out of public title/help-type text. Exact Task/location endpoints still reject external Helpers, even when selected but unconfirmed.

Approximation uses 0.02-degree grid centers, clamped at poles/antimeridian and shifted inside the cell if the representative would exactly equal the stored pair. No stored exact pair is returned. Whole-km distances and radius checks use the public coarse point rather than the exact private location, reducing precise-distance triangulation. This is only an MVP approximation: sparse-area re-identification and robust privacy guarantees need further work. No real maps, geospatial provider or GPS collection exists.

Mobile discovery/Offer/Assignment screens use the ordinary HTTP API. Role preference PATCH only chooses an existing role and updates lastActiveRole; it cannot grant roles or verification and is never an authorization source. The emulator seed provides multiple-role and verified/unverified test users. A persistent My Offers inbox, native map provider and production verification provisioning remain follow-ups.

Paid Tasks follow the generic Offer → selection → pending Assignment model. Direct paid-task acceptance remains an unresolved product decision and has no separate endpoint or financial operation.

## Sprint 2B suggestion boundary

Authenticated AI routes delegate to AiTaskService and an AiProvider interface. Controllers have no vendor SDK calls. AiProvider accepts only user-supplied text, explicit timezone/referenceTime and whitelisted editable saved Task fields; it receives no UID/context/task/location IDs, receiver profile or automatic address data. The provider returns unknown data. The service validates a strict bounded schema derived from draft validation before returning public DTOs. Backend state, unknown fields/enums, invalid dates/numbers and provider Location IDs are rejected as AI_INVALID_RESPONSE.

AI_PROVIDER defaults to disabled; only an explicit mock in a non-production Functions Emulator enables the deterministic MockAiProvider. Unsupported/real configurations remain disabled until a real backend adapter is implemented. It must load secrets on the backend and respect AbortSignal/output bounds. No secret or provider SDK exists in Expo. Existing manual routes do not depend on provider availability. The 8-second provider deadline handles thrown errors, unavailable providers and nonresponsive adapters without logging sensitive provider error bodies. Input is limited to 5,000 characters and the existing 16 KB HTTP body limit; callers cannot choose models/parameters. These are MVP bounds, not distributed rate limiting.

Generation authorizes CREATE_TASK for the care context; when currentTaskId is supplied, EDIT_TASK rights and DRAFT status are also required. Improvement uses the same operation and refuses OPEN/CANCELLED tasks. The service rechecks access and saved updatedAt after provider work. Suggestions contain only editable fields plus derived preview data, server-computed missingFields, warnings, explicit providerMode and optional sourceTaskUpdatedAt. MissingFields uses the same publish validator and includes fields needing correction, not only absent values. No task, event or provenance metadata is written by generation or summary.

The user reviews individual proposed fields; Apply calls the normal authenticated PATCH and never publish. The coordinator compares the current saved updatedAt before PATCH and preserves unselected local form values. This preflight check is not an atomic revision precondition; another editor could still write between GET and PATCH, so backend revision/If-Match support remains a follow-up. All existing draft, compensation, membership and location validation still applies. AI failures and discarded suggestions have no Task mutation path. Accepted changes create ordinary TASK_UPDATED history with changed field names only.

Location wording is matched on the backend against labels in the authorized context using exact case/whitespace-normalized comparison. Only a unique match adds a Location ID. Ambiguous/unmatched wording remains text plus a warning and proposes clearing any old location with null, so readiness requires normal Location selection/creation. The provider cannot authorize or invent an ID.

Timezone is explicit in every request, seeded from the device's IANA timezone (UTC only as a visible fallback), editable by the user and validated on the backend. referenceTime is UTC ISO, never a server-local date. The mock extracts only explicitly offset ISO timestamp pairs; relative wording such as tomorrow afternoon remains uncertain, and an edit can propose clearing old times with a warning. Timestamp ordering and compensation readiness still come from publish validation. Nothing is automatically published for ambiguous times.

Summaries are derived on demand from whitelisted editable Task fields, using normal task read authorization including Draft privacy. Responses carry taskUpdatedAt/generatedAt/providerMode. No server cache or persisted summary exists. Concurrent version changes return AI_STALE_TASK; the detail UI clears summary state when task version changes. Task data remains authoritative.

## Transcript fallback and retention

Speech transcription is deliberately separate from Task extraction. This sprint supports entered/pasted transcript → explicit user review → the same plain-text suggestion API. With no speech provider or native target configured, there is no recording SDK, audio processing/upload path, external audio fetch, microphone permission request or audio retention. TRANSCRIPTION_FAILED has a client message for a future transcription adapter; no current endpoint claims to transcribe audio. Binary audio, audio URLs and provider parameters are rejected by the strict JSON input schema/body limits.

Future native recording must have its own size/duration limits, temporary private processing and cleanup before handing reviewed plain text to AiTaskService. It must not introduce voice_tasks, ai_tasks or another lifecycle. Current prompts/transcripts/responses are transient request/UI memory; only accepted normal Task fields are saved. No raw text/audio/reasoning is logged or added to task_events. No new Task fields or Firestore collections were added in Sprint 2B.

Client Firestore and Storage rules deny all reads and writes, including offers and assignments. Admin bypasses these rules, so backend permission checks are mandatory. Context enumeration queries the current user's memberships, filters active records, then retrieves those contexts. Context Task/location lists query a single authorized context (no composite index required for those queries); tasks are sorted newest-first in memory. Discovery has its separate visibility/status index. Lists have no pagination yet. There are no membership mutation, location edit/delete or invite APIs.

The demo project ID is isolated from real production resources. Emulator token acceptance is controlled by Admin's emulator environment variables, set by Firebase CLI. Never set those variables in production. Storage rules are configured but no bucket client or upload feature exists. Messaging is deferred: no token registration, credentials, permissions or notification delivery is implemented. Branding lives in the mobile config and app metadata, independent from backend role terminology.

Production requires a real Firebase project, explicit HTTPS API configuration and a reviewed deployment setup. CORS is permissive for this development API; authentication and authorization are always enforced. Restrict browser origins before web deployment.

## Sprint 4 lifecycle and privacy

AssignmentService centralizes transition rules and permissions. AssignmentRepository reads Task, Assignment, selected Offer, ACTIVE backup query and actor membership before any writes in one Firestore transaction. Task is the shared serialization document for Offers, selection, lifecycle and Task cancellation. Event IDs are allocated outside transaction retries; only the winning transaction appends events. Repeated invalid transitions return 409, with no duplicate timestamp or event.

Task additions: ARRANGED, IN_PROGRESS, COMPLETION_PENDING, COMPLETED, DISPUTED. Assignment additions: CONFIRMED, IN_PROGRESS, COMPLETION_PENDING, COMPLETED, DECLINED, CANCELLED_BY_HELPER, CANCELLED_BY_REQUESTER, DISPUTED. Every transition checks both expected states, activeAssignmentId and selected Offer relationship. No-show is deferred.

Confirmation: pending/awaiting becomes confirmed/arranged, confirmedAt is set, selected Offer stays SELECTED and all ACTIVE backups become NOT_SELECTED atomically. Before confirmation, decline makes selected Offer WITHDRAWN; requester cancellation makes it NOT_SELECTED. Both clear activeAssignmentId and fall back to HAS_OFFERS with active backups, otherwise OPEN. Confirmed cancellation reopens OPEN and never reactivates stale backups. Explicit reoffering may reactivate WITHDRAWN/NOT_SELECTED records with original ID/createdAt.

Normal Task cancellation is valid only in DRAFT, OPEN, HAS_OFFERS, AWAITING_CONFIRMATION or ARRANGED. It sets CANCELLED, closes all ACTIVE/SELECTED Offers as NOT_SELECTED, zeroes count, clears activeAssignmentId, and cancels pending/confirmed Assignment as CANCELLED_BY_REQUESTER. It emits TASK_CANCELLED and, where applicable, ASSIGNMENT_CANCELLED atomically. Arrangement cancellation keeps the Task needed; Task cancellation does not reopen it. Cancellation after execution starts is deliberately unsupported.

offerCount remains the number of ACTIVE + SELECTED Offer records. Selection preserves it; confirmation reduces it to 1; pending decline/cancellation removes the selected Offer, leaving backup count; confirmed cancellation reduces it to 0; Task cancellation zeroes it. Completed/disputed history retains one SELECTED record and count 1. New Offers cap actionable count at 100. Atomic lifecycle query guards legacy data with a 400-backup maximum to stay below Firestore write limits. Larger datasets require a deliberate migration rather than partial confirmation.

Only assigned Helper confirms, starts and requests completion. Only active Task owner/context manager approves or disputes completion; a manager who is the assigned Helper cannot self-approve/dispute. lastActiveRole remains UI preference. Request completion sets both states COMPLETION_PENDING and completionRequestedAt. Approval sets both COMPLETED and completedAt; activeAssignmentId is retained for history. Dispute sets both DISPUTED; optional 1-500-character reason stays on private Assignment, never public DTO/event. No resolution transition exists.

General Assignment DTOs and caller-scoped My Offers/My Assignments contain relationship metadata only. Helper lists use helperId + updatedAt descending, limit 50 plus a truncation marker; no cursor. Execution read uses a consistent transaction for relationship/authorization/location and only allows the current assigned Helper in paired CONFIRMED/ARRANGED, IN_PROGRESS or COMPLETION_PENDING states. It projects label, formatted address, optional coordinates and safe scheduling/title/help-type fields. General Task.instructions is deliberately excluded because it can contain care/medical information. No unrelated profile or care data is returned. This endpoint is separate from general Task and context Location APIs, whose circle permissions are unchanged.

Pending selection grants no exact location. DECLINED/CANCELLED/COMPLETED/DISPUTED relationships grant no execution access. Prior downloaded data cannot be recalled; development UI clears details on actions/refresh. Existing trusted-circle access is a separate membership capability. Discovery retains its 0.02-degree coarse coordinate projection and only OPEN/HAS_OFFERS published public tasks. Sprint 5A adds transactional in-app Notifications and separate immutable Reviews; no financial or no-show side effects exist.


## Sprint 5A supporting read models and records

Calendar is a service projection over Tasks/Assignments, not a collection. A required increasing UTC/offset date range of at most 93 days filters Task startAt (inclusive start, exclusive end; not overlap semantics). Requester calendar considers at most 20 memberships and 50 scheduled Tasks per active context, uses centralized ownership/active-manager authorization, excludes DRAFT/CANCELLED, and returns at most 100 sorted items. Helper calendar considers the newest 100 relationships and includes only current pending/confirmed/in-progress/completion-pending/completed work in range. Truncation is explicit, including relationship/context bounds; this is not exhaustive pagination. Calendar summaries include title/time/status/role and permitted Assignment/helper IDs, no location/instructions/private context identifiers. UI role preference grants no calendar access.

Task fields publicInstructions/privateInstructions are separately validated optional draft strings (2,000 characters, null clears). Legacy instructions (5,000 characters) remain compatible with Sprint 1-4 clients/AI and are never implicitly reclassified. Publish accepts publicInstructions or legacy instructions. Eligible discovery and the Assignment public-task projection include publicInstructions only. New privateInstructions is visible in owner/active-manager Task reads and the current assigned Helper execution projection; ordinary circle Task reads omit it. Pending, former, completed and disputed execution access stays denied. Legacy general instructions remain excluded from execution and public discovery. Tasks are not a medical-record model. Authors must keep public fields free of private address/health/access details; this MVP does not perform semantic content moderation. AI cannot propose either new privacy field; it continues using reviewed legacy suggestions. Publish readiness internally considers existing public instructions without supplying private operational text to the provider.

Only notifications/reviews collections are added. lifecycleNotifications is a pure Notification-record planner, separate from future delivery adapters. Marketplace and Assignment repositories create records in the same transaction as state and TaskEvent. Notification ID is event ID + recipient ID, with events allocated before retry callbacks; repeated invalid transitions do not write events/Notifications. No actor is notified about their own action. OFFER_RECEIVED and Helper-originated lifecycle changes notify Task creator (the MVP requester-side recipient); HELPER_SELECTED/TASK_COMPLETED/COMPLETION_DISPUTED notify assigned Helper. ASSIGNMENT_CANCELLED notifies the other side. No manager fan-out or older-history backfill is performed. Content is generic and contains no Task private data. Creator-side delegation/preferences are future policy.

Notifications are recipient-scoped and return at most 50 newest records. Mark-read transaction preserves the first readAt. Mark-all considers the newest 200 records atomically and returns truncation metadata, not an unbounded sweep. New Notifications after its snapshot remain unread. Read/navigation still require backend authorization; notification possession never grants Task access. Sprint 7A implements domain transition -> Notification record -> separate FCM delivery service. Device token persistence is backend-only; actual OS push acceptance remains pending.

Review submission checks initialized user, active Task ownership/manager membership, non-self relationship, completed Assignment/Task and current historical activeAssignmentId inside a transaction. SHA-256(JSON([assignmentId,reviewerId])) gives deterministic uniqueness; tx.create plus existence check returns conflict for duplicate concurrent requests. Rating is integer 1-5, optional trimmed comment 1-1,000 characters. Reviews are immutable; each authorized reviewer may submit once per Assignment. No edit/delete/moderation endpoint, reverse review or completion dependency exists.

Helper ratings use replaceable SupportRepository aggregation: Firestore count/average over revieweeId indexes rather than downloading all Review documents. Recent history is limited to 20. No average is emitted for zero Reviews. Public Review DTOs omit reviewer/context/task/assignment IDs and label reviewers generically Requester. Comments are intentionally shared with authenticated app users, so must exclude private information; moderation/retention policy remains future work. Offer review may attach aggregate average/count; discovery avoids review-history queries. Aggregations still incur indexed backend work; denormalized totals can replace this later.

Timeline reads at most 100 recent existing task_events, then maps allowlisted event types to generic labels/timestamps. No second history collection or raw metadata is exposed. Circle access follows Task visibility, including draft privacy. External access requires the caller's own Offer relationship, excludes draft/edit history and competing Offer/selection events, and begins at their relationship timestamp. Responses contain no actor/resource/context/location identifiers or messages. Existing historical global TaskEvent APIs remain unavailable; only this projection is public.

Verification status reads the server User field (legacy default UNVERIFIED), includes actual HELPER-role/VERIFIED discovery eligibility and explanatory copy. No write/upload/provider endpoint exists. Explicit loopback emulator seeds are retained. Centralized support permissions cover initialization, management/review eligibility, timeline scope and Notification ownership; private instruction access reuses confirmed execution authorization. No lastActiveRole check authorizes a resource.


## Sprint 5B frontend organization

Backend/domain/contracts, rules/indexes and all API modules are unchanged. useSession restores Firebase Auth then fetches the existing account automatically, protects against stale bootstrap results and distinguishes first onboarding from service failure. App owns top-level tabs, active circle and the existing role preference. Trusted-circle Task navigation is independent of Helper mode so a Helper-only account can still access authorized circle work. Existing feature coordinators retain API/state/mutation responsibilities; no client lifecycle state machine, Redux, business Firestore or new navigation dependency exists.

Reusable theme/index.ts centralizes approximate palette/spacing/radii/type/weights/shadow/screen width. components/ui.tsx provides accessible Text/Pressable buttons/fields/cards/status/empty/loading/error/info primitives. AppChrome has header and fixed bottom navigation outside the scroll region. Cards composes Task/Offer/Profile views, and utils/presentation.ts maps statuses/roles/dates/safe error copy; backend enum names remain stable. All previous screens use shared primitives instead of unstyled native buttons. System fonts and flexible width/max-width layouts need no static assets or new dependencies.

Keyboard-aware scroll, Android status/bottom spacing and minimum 48-point mutation controls are configured but require actual device acceptance. Task cancellation includes an explicit confirmation. Feature mutations retain synchronous locks and await server success before displaying changes. Current/Drafts/History and My tasks/My offers organize existing results. Assignment title lookup uses only the safe existing relationship projection. Privileged execution data stays local, clears on refresh/actions/unmount/background, and a visibility epoch prevents a pre-background response being displayed after return. Previously viewed information cannot be recalled.

The current Figma design-context/screenshot reads were denied by the Starter-plan tool quota, so no asset or exact token/layout comparison is claimed. Frontend-audit.md records the source, mapping, access failure and delivered scope. A final Figma comparison and native acceptance remain necessary. Future Community/Messaging/financial flows require their own backend slices; this frontend adds no fake persistence or direct paid acceptance.


## Sprint 6A Community boundary

Only community_posts, community_comments, community_likes, resources and resource_saves are added. CommunityRepository owns all Firestore access, CommunityService owns type-specific composition/lifecycle checks, centralized permissions/community.ts applies verification/membership/provenance checks, and strict route schemas reject irrelevant fields. Shared contracts are public projections only. Mobile Community uses existing theme primitives and api/community.ts; Need offer actions call existing api.offerHelp. No second matching, Task state machine, direct paid acceptance or messaging exists.

NEED contains taskId and independent author caption/optional headline; it never automatically snapshots Task title/location/status/compensation. Creation requires active Task creator/context manager, published OPEN/HAS_OFFERS and destination compatible with Task visibility/context. Discovery's exact existing whitelist/coarse location mapper was extracted into discovery/dto.ts and reused without changing discovery behavior. Preview reads current Task/location in the same read-only transaction as Community scope/permissions. Circle Task previews are still coarse, including for circle members. Closing the Task or removing external visibility hides the live preview for ineligible viewers. Private/legacy instructions, exact coordinates/address, care receiver/context/location IDs never enter Need preview DTOs. User-authored captions are public to the chosen audience and require author care; no semantic private-data detector is claimed.

PUBLIC_VERIFIED means initialized authenticated VERIFIED user of any actual role for all public reads/interactions/creation. CARE_CIRCLE requires active membership in the specified context, with trusted unverified access. lastActiveRole is irrelevant. Feed explicitly chooses public scope or one circle; it does not scan a global feed and rely on frontend filtering. Each query is capped at 30 newest results (31st detects truncation), with optional type filter. There is no cursor yet. All detail/comment/Like/Share operations recheck visibility. Dependencies (Task, Resource, original Share) enforce their own current visibility as well, so a circle Share cannot weaken public verification or a private original's membership requirement.

Resource has author, title/summary/category, optional credential-free HTTPS URL, visibility/context, ACTIVE/ARCHIVED status and timestamps. Only ACTIVE readable Resources project; no scraping, downloads, external ingestion or CMS integration. URL is stored/displayed and only explicitly opened by mobile. No archive mutation endpoint is added, but server/admin archival safely hides it. Resource save ID is {resourceId}_{uid}; save checks current visibility, idempotent unsave permits cleaning up one's own save even after access ends. Saved list considers newest 50 records and omits unavailable Resources. No local-only bookmark state or counter coupling to Likes exists.

SHARE stores originalPostId/originalAuthorId, a separate caption and no original content snapshot. Share-of-Share normalizes to the root with a bounded lookup; projection embeds at most one original. Destination must be no wider than a circle source (same context). SHA-256 of [rootId,authorId,visibility,context-or-null] gives one Share per author/root/destination. Duplicate concurrent requests return the existing Share, preserving first caption/timestamps. Source post access is checked in the creation transaction and again on every projection. Missing/unauthorized roots omit original content and original-author/provenance IDs, returning unavailable. Already published independent outer captions cannot be recalled; retention/moderation is future policy.

Like ID is {postId}_{uid}. A transaction reads post/current membership and Like, adds/deletes only when state changes and updates likeCount. Duplicate Likes/unlikes are no-ops and counts cannot decrement below zero. Flat comment creation uses an ID allocated outside retries and atomically writes comment plus incremented commentCount on the same post document; concurrent Like/comment operations serialize there. No edit/delete/reply path exists, so commentCount counts created records and is monotonic. Repeated distinct comment POSTs are distinct comments; no generic idempotency platform exists. UI uses synchronous locks and no automatic write retries.

Community projections use consistent read-only Firestore transactions so source visibility/resource archival and membership changes are checked in one snapshot. Public author IDs plus explicit Member-suffix labels are safe aliases; no invented display names/photos/private profile data. Post detail includes bounded comments, current Like state and current Resource save state. The backend does not expose raw documents. New indexes cover public/circle/type feed ordering, post comments and own saved resources.

Community Notifications are intentionally deferred; Task lifecycle Notifications remain unchanged. ## Sprint 6B Messaging

MessagingRepository is the only Firestore data accessor for this slice. Its write type permits conversations, messages and existing notifications only, so communication cannot write Task/Offer/Assignment or Community state. MessagingService owns get-or-create, idempotent sends, projection/read counters and bounded history. Central permissions/messaging.ts separates participant-only history from canSendConversation; routes only validate and delegate. Frontend uses api/messaging.ts through the same authenticated transport. No direct Firestore/listener, provider SDK or new dependency exists.

Conversation has exactly two unique sorted participant IDs, CARE_CONTEXT/TASK scope, careContextId, optional taskId, creator/timestamps, nullable lastMessageAt, bounded lastMessagePreview, messageCount sequence and two unread counters. Deterministic SHA-256([scope,resourceId,sortedPair]) gives one conversation per circle-or-task and pair. TASK context is derived from the Task, never accepted as a client permission flag. Existing get-or-create may return participant history in read-only mode; no new inactive relationship conversation is created. Task default counterpart is the Task creator when still authorized; requester UI may explicitly choose a Helper. Active managers can initiate their own individual pairs, not a group/fan-out. If creator access ends, another active manager may initiate their own legitimate pair; external Helper is not given a private manager directory.

CARE_CONTEXT creation/new sends require both initialized participants to be ACTIVE members of that exact context. Removed members keep participant-only history/read marking, while sending is blocked for both sides. A separate legitimate TASK scope may still be used; scopes are never implicitly mixed. The new bounded messaging-members endpoint exposes only active member IDs/explicit alias labels to another active member, not raw profiles.

TASK sending requires a published nonterminal Task, an active creator/context-manager requester and a Helper with ACTIVE eligible Offer on OPEN/HAS_OFFERS/AWAITING_CONFIRMATION, or current selected pending/confirmed/in-progress/completion-pending Assignment matching Task state/activeAssignmentId/selected Offer. ACTIVE Offer eligibility reuses existing trusted-circle/external-verified HELPER checks. A current selected Assignment uses its existing assigned identity/state relationship without inventing a new verification policy. Backup ACTIVE Offers may communicate while selection is pending; confirmation's NOT_SELECTED backups become read-only. WITHDRAWN/DECLINED/cancelled/COMPLETED/DISPUTED or cancelled/completed/disputed Task blocks new sends. A genuinely new active Offer can restore the same pair's sending; old participation alone cannot. Helper-to-Helper pairs have no requester-side authority and are denied unless an independent requester relationship truly exists.

Only actual initialized participants may read history, messages and counters, even after relationship removal/termination. Nonparticipant resource-ID guesses do not authorize reads or read marking. History returns no Task/location/private instruction/care-receiver/profile data. TASK summary omits careContextId; CARE_CONTEXT participants may see their known scope ID. Public-safe labels are Member + ID suffix because names/photos do not exist in current contracts. User-authored message text/previews remain private participant content and must not be treated as a medical-record store.

Message contains ID, conversationId, senderId, trimmed plain text, required clientMessageId, server-assigned sequence, createdAt and nullable readAt. Content/identity are immutable; only recipient readAt can change. SHA-256([conversationId,senderId,clientMessageId]) enforces logical-send uniqueness. A participant retry of an already committed identical Message returns that existing result even if sending is now inactive, with no writes; different text for that ID conflicts. New send re-evaluates current users/memberships/Task/Offer/Assignment inside the same transaction as Message creation, Conversation update and NEW_MESSAGE Notification. Task/Offer/member versions therefore participate in retries when termination races a send. No core lifecycle write occurs.

Sequence comes from messageCount under the Conversation lock; send timestamps are monotonic relative to prior lastMessageAt, preventing Inbox reordering on same-time/clock-skew cases. Concurrent distinct sends get distinct sequential positions. Duplicate sends do not alter sequence/lastMessageAt/unread counts/Notification history. NEW_MESSAGE reuses existing notifications with CONVERSATION resource ID and generic body (no Message text/private Task data), only for the other participant. No sender self-notification is added. Sprint 7A separately delivers NEW_MESSAGE through the shared push service.

Inbox is array-contains participant + lastMessageAt descending + createdAt descending, limit 50. Empty conversations use null lastMessageAt and sort after messaged histories. Messages query conversation + sequence descending, newest 50 reversed for display, with before-sequence cursor and explicit truncation. Mark-read transaction selects oldest 200 incoming unread records, sets readAt once and decrements only caller's unread counter exactly. Conversation write serialization prevents lost increments during send/read races. Repeating read is a no-op; oldest remaining batches are explicit. Own Messages are never read-marked by the sender. Message unread and Notification unread are distinct product histories.

Mobile Inbox is a small overlay in the existing shell, with Task-update navigation preserved. MessageEntry integrates Circle member/Offer/Assignment paths; Notification CONVERSATION routing opens the same history screen. Conversation uses initial HTTP load + explicit refresh, older-page loading, left/right text bubbles, real timestamps/read flags and synchronous send locks. Logical send IDs survive an in-screen failure/retry for unchanged trimmed text; no offline outbox or persistent draft system is claimed. Refresh/read operations run only by visible screen/action; no periodic polling, WebSockets/SSE, presence or typing state. Native keyboard/scroll acceptance remains pending.

Future trust/safety decisions include reporting/blocking/moderation, account deletion/history retention, medical-sensitive user text, abuse limits and contact policy. Group chat, attachments, voice, reactions, editing/deletion, E2E encryption infrastructure and production transport are deliberately absent. Native push delivery infrastructure is now implemented in Sprint 7A, with OS acceptance pending. Community/Review comments remain independent.

TaskRepository publication and AssignmentRepository terminal transitions prepare PointRepository ledger writes inside the same resource/permission transaction; all reads finish before writes. Immutable entries plus cached private account summaries use deterministic logical source IDs. No payment/provider library, direct mobile Firestore, or Maps/discovery wallet projection.
