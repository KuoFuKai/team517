## Models, authority and public API

Backend-only `point_accounts/{userId}` caches integer availablePoints, reservedPoints, lifetimeEarnedPoints, lifetimeSpentPoints and timestamps. An absent account returns a valid zero projection; first mutation creates it transactionally. Account mutation is backed by create-only immutable `point_transactions` containing owner, type, amount, available/reserved/earned/spent deltas, source identity, Task/Assignment references and timestamp. All writes pass through repository transactions; there is no edit/delete/grant mobile endpoint. Ledger deltas reconstruct the summaries (verified in tests). Grants do not count as earned task rewards.

Transaction types: GRANT, RESERVE, RELEASE, TRANSFER_OUT, TRANSFER_IN, ADJUSTMENT. ADJUSTMENT is only a reserved internal type/projection; no adjustment endpoint or UI exists. Completion creates paired TRANSFER_OUT/TRANSFER_IN records with one Task source, also referencing the completed Assignment. Logical identity is deterministic per type/source/user and collisions with differing amounts fail. Records are never overwritten on replay.

`GET /api/v1/me/points` returns only the caller's four balance fields. `GET /api/v1/me/points/transactions?cursor=…` returns 20 owner-only public entries, explicit nextCursor when another page exists, friendly type/amount/deltas/date; no source metadata, other-owner information, Firestore paths or private Task data. History uses userId/createdAt/document-ID ordering and a deployed composite index. A cursor must reference the caller's own immutable entry; malformed/foreign cursors fail. Direct mobile Firestore access stays denied, including both new collections. No `lastActiveRole` authorization.

## Lifecycle policy

The Task creator funds its reward even when an authorized Care Manager publishes/completes/cancels for them. A draft reserves nothing; reward edits remain draft-only. Publish atomically validates the normal Task and reserves its pointReward: available −N, reserved +N, then opens the Task with its normal event. Insufficient points returns INSUFFICIENT_POINTS, leaving the Task DRAFT with no partial ledger/event/balance mutation. The UI keeps the saved draft and shows safe required/available amounts. A repeated POINTS publish returns current published state without reserving again. Non-POINTS behavior is preserved.

Reservation belongs to the Task, not an Offer or Assignment. Offers, withdrawals, selection, pending decline/cancellation, confirmed cancellation and replacement selection never release it while the Task stays open/arranged. Full Task cancellation before execution releases reserved points back to available in the same lifecycle transaction. Repeated POINTS cancel returns the cancelled Task without double release.

Requester/authorized manager completion approval atomically completes Task/Assignment, consumes creator reserved points, credits the completed Helper's available/lifetime-earned points, increases creator lifetime-spent, and creates the paired ledger entries. The Helper cannot self-settle. Repeated POINTS approval is a no-op balance/event replay; both competing approvals can safely succeed with one transfer pair. All lifecycle writers lock the Task and account documents, so competing publications cannot overspend. Cancel versus completion follows existing lifecycle restrictions: ordinary cancellation is unavailable after execution starts.

DISPUTED holds the reservation. No automatic refund, split, credit, arbitration or post-completion reversal exists. COMPLETED settlement is final for this MVP. Legacy unfunded published POINTS tasks fail closed with POINTS_RESERVATION_MISSING rather than minting/charging silently. Read-only bounded Preview inspection found no active unfunded legacy tasks; existing data was not wiped or rewritten.
